Bundless Usage Docs

Build more. Bundle less. Bundless lets React JSX and TypeScript run directly in the browser without a build step, then keeps a path to Webpack when bundling becomes a better deployment choice.

Quick start

Serve this file over HTTP. Bundless transforms the JSX script and appends a module script.

<!doctype html>
<html lang="en">
  <head>
    <meta charset="utf-8">
    <meta name="viewport" content="width=device-width, initial-scale=1">
    <script type="importmap">
      {
        "imports": {
          "react": "https://esm.sh/react@17.0.2/es2022/react.mjs",
          "react-dom": "https://esm.sh/react-dom@17.0.2/es2022/react-dom.mjs"
        }
      }
    </script>
  </head>
  <body>
    <div id="react-root"></div>

    <script type="text/babel">
      import React from "react";
      import ReactDOM from "react-dom";

      function App() {
        return <h1>Hello from Bundless</h1>;
      }

      ReactDOM.render(<App />, document.getElementById("react-root"));
    </script>

    <script src="/dist/bundless.acorn.min.js" type="module"></script>
  </body>
</html>

Runtime/import behavior

HTML scripts

Put app code in an external or inline script with type="text/jsx" or type="text/babel", then load one Bundless runtime. On document ready, Bundless fetches external scripts or reads inline scripts, transforms the code, and appends module scripts to the page.

Import maps and package imports

Add an import map for bare imports such as react and react-dom. Default imports use bundler-style interop: Bundless binds to the module's own default export when that property exists, and otherwise falls back to the module namespace. Falsy defaults such as false and null are preserved.

Named imports remain strict, namespace imports bind to the module namespace, and side-effect imports load the module without creating a binding. 

<script type="importmap">
  {
    "imports": {
      "react": "https://esm.sh/react@17.0.2/es2022/react.mjs",
      "react-dom": "https://esm.sh/react-dom@17.0.2/es2022/react-dom.mjs"
    }
  }
</script>

Local app modules

Local static imports with .mjs, .js, .jsx, .ts, or .tsx extensions are resolved against the current file and loaded through window.import(). Cache-busting query strings remain part of the module cache key. 

import React from "react";
import Counter from "./Counter.jsx";
import "./analytics.js";

export default function App() {
  return <Counter />;
}

window.import(url)

const module = await window.import("./Dialog.jsx");
module.openDialog();

window.import() normalizes the URL, fetches the source, transforms it, evaluates it as a blob module, and resolves to the module namespace. Concurrent and repeated imports for the same normalized URL share the same promise and resolved module; failed imports are evicted so a later call can retry.

Prefetching

window.Bundless.prefetch(urlOrUrls)

await window.Bundless.prefetch(["./Dialog.jsx", "./Settings.jsx"]);

Use this when you know a module will probably be imported soon. It fetches and warms the source cache only; it does not transform, evaluate, or resolve to a module namespace.

data-bundless-prefetch

<script type="application/json" data-bundless-prefetch>
  [
    "./Dialog.jsx",
    "./Settings.jsx"
  ]
</script>

Use this for startup preparation from HTML. The JSON must be an array of module URL strings. Bundless fetches and transpiles the listed modules without evaluating them; a later window.import() call reuses the prepared code and then evaluates the module.

Troubleshooting

Modern browser surface

Bundless depends on modern browser features: ES modules, dynamic import(), fetch(), blob module URLs, top-level await, and import maps when you use bare imports.

Production constraints

Runtime transformation means the browser fetches and compiles application source before the app is fully ready. That can be fine for prototypes, small internal tools, docs, demos, and static multi-page apps, but it is real startup work and should be measured on the devices and networks you care about.

Restrictive CSPs may block Bundless because it inserts inline module code and window.import() evaluates transformed modules through blob: URLs. If your runtime, React imports, or application modules come from another origin, your policy also has to allow those fetches and module loads. Cross-origin source files must return CORS headers that allow your page to read them.

Source-map payload

Acorn and Meriyah .dev.js builds include runtime inline source maps for easier debugging. Their .min.js and .prod.js builds omit runtime inline source maps to avoid production size and runtime overhead. Babel and Sucrase have their own single-build source-map behavior, described in the runtime table.

Preact mode

Add to="preact" to a supported Bundless runtime tag to transpile React-style code toward Preact.

  • Preact portals require a concrete DOM element.
  • Preact context consumers need a matching provider.
  • Preact emits regular DOM events; for direct form handlers, read values synchronously from e.currentTarget.value.
  • Refs can differ by pattern; check whether you received a DOM node or a .current object before calling focus().

Babel standalone

The Babel runtime is useful when you need Babel standalone coverage in the browser, but Babel's own standalone docs recommend a Node-based build system for production transpilation. Treat it as a convenience path, then move to Webpack when production constraints show up. Babel standalone docs

Move to Webpack

Webpack is the escape hatch: keep literal window.import() calls and supported window.Bundless.prefetch() calls in your app, then add a build when runtime work, dependency control, or deployment policy calls for one. 

const path = require("node:path");
const BundlessWebpackPlugin = require("bundlessdev/webpack");

module.exports = {
  entry: "./src/index.jsx",
  module: {
    rules: [
      {
        test: /\.[jt]sx?$/,
        exclude: /node_modules/,
        use: {
          loader: "babel-loader",
          options: {
            presets: ["@babel/preset-react"],
          },
        },
      },
    ],
  },
  plugins: [
    new BundlessWebpackPlugin({
      include: path.resolve(__dirname, "src"),
      prefetch: "webpack",
      stripHtmlRuntime: true,
    }),
  ],
};

Migration checklist

  • Keep ordinary application imports, literal window.import() calls, and supported source-level window.Bundless.prefetch() calls.
  • Configure a normal Webpack entry and the project's JSX or TypeScript loader.
  • Add new BundlessWebpackPlugin() to plugins.
  • Remove browser bootstrap and source script tags, or let HtmlWebpackPlugin stripping handle generated tags.
  • Move declarative prefetch JSON to source-level window.Bundless.prefetch() calls when Webpack hints are wanted.

How the pieces fit

The plugin is the normal migration path: it adds the Bundless pre-loader, aliases browser runtime imports away by default, and strips Bundless bootstrap tags from HtmlWebpackPlugin output when HtmlWebpackPlugin is present. The loader is only the source rewrite step, useful when you want manual rule placement. Neither the plugin nor the loader transpiles JSX or TypeScript for your bundle; keep your normal Babel, SWC, esbuild, or TypeScript loader.

What happens to source calls?

When window is not lexically shadowed, window.import("./Dialog.jsx") is rewritten to native import("./Dialog.jsx"), so Webpack owns resolution, chunks, and runtime loading. Use literal strings for imports you expect Webpack to split cleanly; dynamic arguments follow Webpack's normal dynamic-import limits.

With the default prefetch: "webpack", window.Bundless.prefetch("./Dialog.jsx") or an array literal of string entries becomes Webpack prefetch hints plus a resolved promise. Unsupported or dynamic prefetch arguments become a resolved promise with no hint, and transformed prefetch calls do not evaluate modules.

What happens to HTML?

With stripHtmlRuntime: true, HtmlWebpackPlugin output drops Bundless runtime script tags, Bundless source script tags, and unignored data-bundless-prefetch blocks. Declarative prefetch JSON is not converted into Webpack hints; move wanted hints into source-level window.Bundless.prefetch() calls. A data-webpack-ignore attribute preserves only declarative prefetch blocks, not runtime or source script tags.

Webpack API reference

Advanced options

loader
Default: enabled because the option is unset. Set exactly false to skip the automatic enforce: "pre" loader rule.
test
Default: /\.[cm]?[jt]sx?$/. Used as the generated pre-loader rule's test.
include
Default: unset. When truthy, copied to the generated pre-loader rule's include.
exclude
Default: /node_modules/. When truthy, copied to the generated pre-loader rule's exclude; a falsey override omits exclude.
parserPlugins
Default: unset. Entries are appended to the built-in Babel parser plugins: jsx, dynamicImport, importMeta, topLevelAwait, classProperties, classPrivateProperties, classPrivateMethods, objectRestSpread, optionalChaining, nullishCoalescingOperator, numericSeparator, logicalAssignment, and importAttributes. Files matching /\.[cm]?tsx?$/ also receive typescript.
prefetch
Default: "webpack". Use "webpack" for Webpack prefetch hints from supported literal calls, or "noop" to keep the promise shape without hints.
runtime
Default: false. When exactly false, the plugin installs runtime aliases to false; any other value skips alias installation.
runtimeAliases
Default: unset. When runtime === false, unset uses the built-in alias map: bundlessdev$, bundlessdev/acorn$, bundlessdev/acorn/dev$, bundlessdev/babel$, bundlessdev/meriyah$, and bundlessdev/sucrase$ all resolve to false. Supplying runtimeAliases replaces that map. The plugin merges these aliases before existing resolve.alias entries, so aliases already in your config win.
stripHtmlRuntime
Default: true. Set exactly false to stop HtmlWebpackPlugin stripping of Bundless runtime tags, Bundless source tags, and unignored declarative prefetch blocks.

Transformer limits

  • The transformer does not transform calls when window is lexically shadowed.
  • window.import() rewrites its callee to native import() and therefore uses Webpack dynamic-import semantics.
  • Prefetch hints are generated only for a string literal or array literal string entries.
  • Unsupported or dynamic prefetch arguments become a resolved Promise with no hint; prefetch: "noop" also returns a resolved Promise.
  • Transformed prefetch calls do not evaluate modules.

Public Webpack exports

BundlessWebpackPlugin

const BundlessWebpackPlugin = require("bundlessdev/webpack");

module.exports = {
  plugins: [new BundlessWebpackPlugin()],
};

This is the standard export and standard use. Webpack calls the plugin lifecycle internally during the build.

bundlessWebpack(config, options)

const { bundlessWebpack } = require("bundlessdev/webpack");

module.exports = bundlessWebpack(
  {
    entry: "./src/index.jsx",
  },
  {
    include: require("node:path").resolve(__dirname, "src"),
  }
);

This helper returns a shallow copy of config with new BundlessWebpackPlugin(options) appended to plugins.

bundlessdev/webpack/loader

module.exports = {
  module: {
    rules: [
      {
        enforce: "pre",
        test: /\.[cm]?[jt]sx?$/,
        exclude: /node_modules/,
        use: {
          loader: "bundlessdev/webpack/loader",
          options: {
            prefetch: "webpack",
          },
        },
      },
    ],
  },
};

Use the loader manually only when loader: false is set on the plugin or when the transform needs custom rule placement.
